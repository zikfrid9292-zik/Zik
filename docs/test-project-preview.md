# READ-only исследование и PREVIEW: проект `Test`

## Что подтверждено сейчас

* Репозиторий содержит только initial commit с однострочным README; файлов V1/V2/V3
  и MCP-инструментов для анализа нет.
* Локального `.env` и `BITRIX_WEBHOOK_URL` нет. Поэтому существование проекта,
  задач, шаблонов, scopes и доступность методов **не проверены на портале**.
* Официальная документация подтверждает четыре типа Gantt-связей и штатный перенос
  зависимой плановой даты при изменении ведущей задачи. Это общая возможность
  продукта, а не результат проверки конкретного портала.

## Сравнение механизмов

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| A. Gantt-зависимости | Нативно, без хостинга; FS переносит следующий этап | Нужно проверить тариф, права и реальное поведение deadline | **Основной** |
| B. Бизнес-процесс | Удобно запускать создание всей структуры | Сам по себе не лучший механизм постоянного пересчёта дат | Только запуск после отдельного этапа |
| C. Робот/триггер | Реакция на изменения в задачах | Настройка зависит от тарифа; сложнее цепочки | Резерв |
| D. Локальный event handler | Полный контроль и верификация | Публичный endpoint, идемпотентность, эксплуатация | Только fallback |
| E. Гибрид | БП создаёт, Gantt переносит, агент проверяет | Больше компонентов | Целевой вариант после проверки |

Выбор: сначала проверить штатную цепочку `finish-start`. Если перенос плановых дат и
нужного deadline на данном портале соответствует ожиданию, внешний обработчик не
нужен. Если Gantt переносит только `START_DATE_PLAN`/`END_DATE_PLAN`, но бизнесу
необходим перенос `DEADLINE`, минимальный fallback — outbound event изменения задачи
и идемпотентный локальный обработчик, который вычисляет дельту и обновляет только
последующие задачи после отдельного preview/confirmation для установки механизма.

## PREVIEW (не выполнено)

После получения READ-результатов и явного подтверждения предполагается:

1. Использовать существующий проект `Test` или остановиться при неоднозначном
   совпадении; проект автоматически не создавать.
2. Создать одну головную задачу `Test` в найденном проекте, только если точного
   подходящего объекта нет.
3. Создать согласованный пользователем набор этапов как подзадачи (`PARENT_ID` = ID
   головной задачи) с `START_DATE_PLAN`, `END_DATE_PLAN`, `DEADLINE`, длительностью и
   ответственными. Названия, длительности и ответственные пока отсутствуют, поэтому
   execution-план ещё неполон.
4. Между соседними этапами создать связи Finish-to-Start (`linkType=2`):
   `этап 1 → этап 2 → … → этап N`.
5. Проверить каждую задачу и каждую Gantt-связь повторным READ; затем провести
   контролируемую проверку сдвига на тестовой цепочке.

### Предполагаемые WRITE-методы после будущего подтверждения

* `tasks.task.add` — головная задача и подзадачи;
* `task.dependence.add` — последовательные FS-связи;
* возможно `tasks.task.update` — только если интеграционная проверка покажет, что
  deadline требуется синхронизировать отдельно.

На текущем этапе эти методы не реализованы в transport API и не вызывались.

### Затрагиваемые объекты

Проект `Test` (только привязка, его даты не меняются), новая головная задача,
согласованные подзадачи и Gantt-связи. Шаблон бизнес-процесса сейчас не создаётся.

### Риски

* несколько проектов/задач с именем `Test`;
* отсутствие scope `task`, `sonet_group`/соответствующего scope или `bizproc`;
* права владельца webhook отличаются от scopes;
* Gantt может переносить плановые даты, но не deadline в ожидаемой конфигурации;
* календарь рабочих дней (`MATCH_WORK_TIME`) меняет фактическую величину сдвига;
* циклическая или уже существующая связь;
* частичное выполнение серии запросов.

### Откат

Откат является отдельной DELETE-операцией: сначала отдельный DELETE PREVIEW со
списком созданных ID, затем отдельное подтверждение. Порядок: удалить созданные
связи, затем только созданные агентом подзадачи, затем созданную агентом головную
задачу. Существующий проект и существующие задачи не удаляются. Для частичного сбоя
используется журнал созданных ID; автоматического удаления без подтверждения нет.
